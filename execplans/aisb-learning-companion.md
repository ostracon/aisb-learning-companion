# Build a local-first AISB learning companion

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

AISB did not contain a `PLANS.md` or an ExecPlan convention when this document was created. This plan is deliberately self-contained for the companion repository, but implementation also requires a separately configured AISB checkout. A contributor should be able to begin with the companion checkout, this file, and any valid AISB worktree. Record every material change at the bottom as a plan revision note.

## Purpose / Big Picture

After this work, a bootcamp participant can open one visually deliberate localhost web application and orient themselves for the week, see the learning outcomes for a day or lesson, move into a specific scheduled session or repository section, take notes without fearing data loss, hand real file work to VS Code, and ask a scoped Codex tutor for help. An optional review coach turns the same outcome set into active-recall sessions and records advisory review progress. Source-control work stays in VS Code or the terminal rather than becoming another application workflow.

The companion is a coach and workbench, not an answer generator. It uses the participant-facing curriculum, the participant's own work, notes, local schedule, prior permitted chats, and locally cached references. Canonical solutions, hidden tests, and folded reference answers are excluded from normal retrieval and model file access as spoiler hygiene, so the assistant does not take the answer key as its shortcut. That does not prevent a capable model from independently deriving the same answer. The actual teaching behavior comes from the coaching prompt, progressive UI, and repeatable behavioral evals, with that limitation disclosed honestly. A context inspector beside each chat makes supplied and withheld sources visible.

The completed experience is visible at `http://127.0.0.1:7575/` and has two first-class, back/forward-navigable modes. **Today** is calendar-led: it shows Day 0 preparation plus the seven scheduled programme days, hides breakfast/lunch/dinner by default, anchors to the active or next non-meal event, and presents the schedule, mapped outcomes, progress, notes, and tutor. **Study** is repository-led: it shows the stable AISB day/section hierarchy, begins each section at its `README.md`, safely follows participant-facing Markdown links, and keeps the notes editor beside the material. Schedule-to-curriculum links are explicit conveniences rather than the source of repository structure, so schedule drift cannot hide or rename course content. The tutor stays in the same shell but receives a fresh server-resolved context envelope for the active mode: schedule/event context in Today, or repository day/section/document context in Study, together with canonical outcomes, safe file descriptors, and the live note draft.

The application is intentionally a thin learning companion, not an IDE or a replacement file browser. It owns orientation, crash-safe Markdown capture, a small safe curriculum reader, outcome progress, review, tutor context, preparation provenance, and one-click handoff. VS Code remains authoritative for general Markdown editing, code, search, Git inspection, terminals, tests, and arbitrary repository navigation. Every saved note can open directly in VS Code; a coding section can create the exact declared participant answer file if absent and open it with `<aisb-root>` as the workspace. The web UI does not grow resizable IDE panes, an embedded terminal, a general-purpose tree, source control, or broad file mutation merely because VS Code already provides them better.

Ad-hoc capture asks for a short name and creates one predictable file such as `day0_quicknote_setup-questions.md`; it does not manufacture a new timestamped file for every click. A note selector lists the current scope's existing Markdown files so the participant can return to and edit them. Browser back, forward, hard reload, and reopening the app restore the same location and the saved workspace scroll position. Notes survive browser or backend crashes. A user-started preparation page deterministically inventories verified curriculum HTTPS links and may explicitly cache bounded public HTML/PDF bytes; HTML receives an inert, content-addressed Markdown projection, while PDFs remain byte-only in v1. Matching verified Markdown projections become optional untrusted context for the active Study section or selected Today event. A separate, explicit visual-aid page lets the participant write and review one pedagogical brief before a single Image API request; it does not generate from ordinary tutor, review, manager, or preparation activity. A durable manager chat can review bounded schedule, notes, outcome progress, review summaries, prepared references, and prior tutor excerpts without gaining access to protected answer sources.

On each full document load, the shell samples the device clock once for `NowAnchor` navigation and interprets that instant against the programme's fixed `Europe/London` time zone. On the unqualified home route it selects the applicable programme day and scrolls the schedule to the active or next item; an explicit deep link keeps its requested route. That clock-derived anchor is frozen: elapsed time never changes the selected day, highlighted session, route, or scroll position. Only an explicit “Sync to now” action or a browser refresh takes another `NowAnchor` navigation sample. The action is view navigation only; it never edits the local schedule, polls a service, or contacts Google. Ordinary timestamps for newly created notes, chat messages, saves, and audit records still use their actual action time but cannot update this anchor.

When the participant wants to concentrate on writing, the week/day sidebar, schedule or material region, learning-outcome region, and tutor/chat pane are collapsible. A single “Focus notes” action hides the surrounding learning chrome and expands the note editor; leaving focus mode restores the participant's prior arrangement. This remains a small set of semantic show/hide controls rather than a pane-layout manager. Collapsing is presentation only: it never discards a draft, stops a chat turn, changes the selected event/document, or recomputes the frozen time anchor.

## Surprises & Discoveries

- Observation: an unresolved durable submission is not by itself proof of uncertain delivery; it is also the normal write-ahead state of every healthy active tutor turn.
  Evidence: the screenshot was captured about 2.5 seconds before that exact nonce completed normally, while `GET /api/tutor/session` advertised it as `active_turn`. Rendering the recovery card from “submission without terminal record” alone therefore made both controls misleading: Check correctly observed the same active turn, and Abandon correctly refused a locally running turn. A later image-only request also demonstrated that visible polling must not reuse the blocking “Restoring this session…” state and that a ten-minute native interruption can leave a genuinely recoverable WAL record after the local active handle is gone.

- Observation: route-level splitting helps the initial client graph, but cannot remove the generic Vite raw-chunk warning without deferring core notebook behavior or merely rearranging eager vendor bytes.
  Evidence: lazily loading all four already-separated secondary pages deferred 29.62 kB raw / 7.65 kB gzip of JavaScript and 14.24 kB raw / 2.23 kB gzip of CSS. Source-map inspection of the remaining 614.27 kB eager chunk showed that its largest contributors are ReactDOM, the router, Zod reached through the active note model, the 86 kB workspace shell, and safe-Markdown parsing/rendering used by Study and note preview. Manual vendor chunks would still be fetched at bootstrap; moving the monolithic primary workspace or Markdown renderer behind another asynchronous boundary is a wider UX change and was deliberately deferred.

- Observation: this is a greenfield web surface and should not be embedded in AISB. There is no first-party JavaScript or TypeScript application, package manifest, schedule database, or existing app directory.
  Evidence: the AISB root contains curriculum folders, Python utilities, and build scripts; a search found no first-party `package.json`, Vite/Next configuration, or schedule fixture. Its development-container port forwarding does not automatically apply to the sibling companion repository; the companion owns its host-local start and any future dev-container configuration.

- Observation: AISB has a root `AGENTS.md`, but it is a symbolic link to the authoring-oriented `CLAUDE.md`. That document explains how solution files work; it does not itself promise student-safe tutoring.
  Evidence: `AGENTS.md -> CLAUDE.md`, and `CLAUDE.md` describes `*_solution.py` as the source of truth for participant instructions and instructor references.

- Observation: the checked-in `.agents/skills/exercise-walkthrough/SKILL.md` supplies the missing teaching contract. It forbids opening `*_solution.py`, reading `*_test.py` in advance, reading later exercises early, or revealing folded hints and answers before a genuine attempt.
  Evidence: the skill's progressive-reading and anti-pattern sections state these constraints explicitly. Its `agents/openai.yaml` disables implicit invocation, so the general companion prompt must restate and enforce them even when the user has not invoked the skill by name.

- Observation: excluding solution filenames is not sufficient. Generated `*_instructions.md` documents contain `<details>` bodies labelled Answer, Solution, Reference solution, and Hint.
  Evidence: these folds are intentionally visible only after a participant attempts a task. The curriculum parser and retrieval index must classify each fold as gated content instead of indexing an instruction file as one unrestricted blob.

- Observation: an AISB checkout may already contain participant changes before the companion starts.
  Evidence: the initial development checkout contained both modified and untracked participant work. All implementation tests preserve pre-existing paths; the companion performs no staging or other Git mutation.

- Observation: the live AISB checkout can change independently while the companion is being built, so an initial dirty baseline cannot be treated as permanent runtime state.
  Evidence: later read-only audits observed the checkout on a different participant branch and commit without any companion-owned Git mutation. Runtime context re-reads repository identity and HEAD for curriculum staleness, but offers no source-control action.

- Observation: an AISB participant checkout may distinguish a participant remote from the public curriculum remote, and participant instructions may use broad staging commands.
  Evidence: that distinction and the risks of broad staging reinforce the decision to leave the established Git workflow in VS Code or the terminal rather than recreate it in the companion.

- Observation: Codex App Server provides the needed thread, turn, streaming, model, approval, interruption, history, and instruction-source primitives, but the command and its generated bindings are explicitly experimental and version-specific.
  Evidence: installed `codex-cli 0.142.3` offers `codex app-server`, `generate-ts`, and `generate-json-schema`. The official app-server documentation says generated artifacts match the exact binary version and labels WebSocket transport unsupported for production.

- Observation: ChatKit can run against a custom server, but it does not natively speak the Codex App Server JSON-RPC protocol. Using it would add a second thread/presentation model and an event adapter.
  Evidence: the current ChatKit custom-server guide requires a ChatKit server and store, while Codex App Server already owns threads, items, tools, approvals, and history. A bounded prototype is needed before accepting that duplication.

- Observation: the initial Calendar access test recorded only a count and date window, not a reusable implementation payload.
  Evidence: a later local seed established the zero-network schedule path. For public distribution, the tracked seed is a generalized example containing no speaker attribution, exact venue/accommodation, Google identifiers, descriptions, attendees, conference links, attachments, event URLs, or authentication material.

- Observation: the curriculum already contains deterministic learning and workspace metadata, but not every schedule item is guaranteed to map to it.
  Evidence: section READMEs carry category-specific prerequisite/outcome tables, and many generated participant instruction files explicitly say “Create a file named `dayD_answers.py`” inside the section directory. Therefore canonical outcomes and participant targets should be parsed without a model when present, while missing/ambiguous event outcomes or filenames must remain visibly unresolved or AI-suggested rather than guessed.

- Observation: Codex App Server supports a per-turn structured-output contract suitable for preparation and review artifacts.
  Evidence: the current official App Server turns documentation defines `turn/start.outputSchema` and states that it applies only to the current turn. Persisted history can be recovered through the dedicated paginated `thread/turns/list` and `thread/items/list` methods after a non-ephemeral thread is read or resumed. The application must still validate the returned payload and enforce source policy itself.

- Observation: current OpenAI documentation supports image generation through the Image API and as a Responses API built-in tool, but does not establish a Codex App Server Imagegen contract for this application.
  Evidence: the official image-generation guide recommends the Image API for one image from one prompt and the Responses API for conversational, multi-turn image work. This companion needs single supplemental learning visuals in its MVP, while Codex App Server must remain the protected text/conversation authority. Therefore image generation belongs behind a separate typed backend provider and cannot be assumed to share Codex authentication or tool permissions.

- Observation: a continuously advancing “current session” marker would be actively harmful during an over-running lesson or an informal schedule change.
  Evidence: the participant explicitly asked for date/time orientation on load but no automatic movement afterward. The safe interaction is therefore a frozen clock snapshot with manual resynchronization, independent of schedule editing or any external Calendar connection.

- Observation: programme-day numbering and repository-day numbering are not the same authority, and treating them as one caused the initially empty Day 5 UI.
  Evidence: the full tracked seed labels programme Day 4 as schedule-only (`curriculum_kind: "break"`) and programme Day 5 as a content day. The current AISB checkout has no `5.*` directories because those materials are historically numbered `4.*`. Today therefore needs an explicit reviewed projection from programme Day 5 to repository Day 4, while Study must independently enumerate the repository's actual Day 0 and numbered section folders. An empty Today mapping is valid; an empty Study tree caused by calendar numbering is not.

- Observation: the ambient shell Node is below the application's supported floor even though a suitable bundled runtime is available.
  Evidence: `node --version` reports `v20.12.2`, while the bundled workspace runtime reports `v24.19.0`; the package, `.nvmrc`, and plan require Node 22.12.0 or later. Implementation tests/install/builds therefore use the bundled Node 24 runtime, while the product compatibility floor remains Node 22.12.0 rather than silently becoming Node 24.

- Observation: App Server named permission profiles are sufficient for the current tutor boundary when selected and verified on every start/resume/turn, but the isolated process still needs an authenticated account cache.
  Evidence: production now creates an isolated Codex home, copies the already authenticated local `auth.json` cache privately without reading or logging it, disables network/apps/memories/plugins, requires the exact allowed `aisb-tutor` profile, and refuses a substituted/missing profile. Native history is intentionally `save-all` inside that isolated home so non-ephemeral tutor threads can resume. An opt-in live `command/exec` probe opened a permitted README and failed to open a solution file, the companion checkout, and the isolated auth cache. The state root is denied to model tools; the cache-copy mechanism is an application bootstrap detail rather than model context.

- Observation: restart recovery cannot safely infer a missing turn from one `thread/read` response.
  Evidence: App Server exposes dedicated paginated `thread/turns/list` and `thread/items/list` methods, and a turn may be summarized or not yet visible while persistence catches up. Production recovery now exhausts bounded pages, hydrates partial item views, locates only the browser `clientUserMessageId`, projects only final assistant messages, and leaves a local submission pending when there is no match. Deterministic tests cover later-page matches, item pagination, repeated cursors, native misses, partial reconciliation, failed turns, and empty final replies; the authenticated process-restart test proves the configured native persistence path.

- Observation: conditional autosave must rebase a newer editor value after an older in-flight disk save acknowledges; merely ignoring the old completion loses the only valid next base hash.
  Evidence: the hook now serializes disk PUTs and binds each completion to note generation and edit sequence. On a valid acknowledgement it checkpoints the new revision/hash, rewrites the latest IndexedDB draft against that exact base, and queues another conditional save when the editor advanced. Route changes cannot update the new note; conflicts preserve the submitted disk copy and latest browser draft. Deterministic hook tests exercise these races, and browser QA observed distinct day/event Markdown paths reaching `saved disk` and surviving navigation.

- Observation: viewport width is not a reliable proxy for the usable Study canvas when both outer rails are open.
  Evidence: at 1200×900 the overall viewport remained above the original media breakpoint while the centre workspace was only 500px and the two-column material/notes grid collapsed its material column to zero. A container-width rule now stacks the panes when the actual workspace is at most 42rem; QA passed at 1200×900, 1440×900, and 900×800 without horizontal clipping or overlap.

- Observation: schedule-to-curriculum mapping is most useful as a quiet bridge, not another navigation system.
  Evidence: a persistent checklist or controls inside every timeline row competed with the schedule and recreated the interface-wrangling problem the companion is meant to avoid. The implemented Today surface shows one cardless “Study material” ledger line only for the explicitly selected event. Editing expands a bounded checklist on demand; linked titles are ordinary routes into Study, and browser Back restores the same event/link/outcome scope.

- Observation: a successful bundle is not proof that the packaged server can start in its intended mode.
  Evidence: the final compile-only gate produced valid client and server artifacts, but an actual `npm start` inherited the configuration default of `development` and tried to load bundled Vite middleware from an invalid generated path. The start script now sets `NODE_ENV=production`, the server build leaves Vite external as a development-only dependency, and the same command was then used for the complete production-browser matrix. Future release gates must include an actual packaged-server listen/health smoke, not just `vite build` and `tsup` exit status.

- Observation: a localhost fetch can fail transiently even though the accepted editor value is already safe in IndexedDB, and a candidate state root can look indistinguishable from the durable live notebook if a test URL is handed to the participant.
  Evidence: the browser reproduced `TypeError: Failed to fetch` on the first note PUT and succeeded on an exact replay, while the note store's unchanged-body check made a lost-response replay idempotent before CAS. During release QA, participant notes were found intact in an isolated candidate state root after the durable live root showed only its initial template. The note was restored through the live revisioned API without deleting either copy. Release work must keep candidate URLs private, identify the state root explicitly, and never present a disposable state root as the live notebook.

## Context and Orientation

There are two repository roots. `<companion-root>` is the application repository, normally `<dev-root>/aisb-learning-companion`. `<aisb-root>` is the separately managed curriculum/participant worktree, normally `<dev-root>/aisb`, resolved through the path contract above. Scripts must not assume either path.

At `<aisb-root>`, `README.md` describes the seven-day curriculum and participant Git workflow. `AGENTS.md` links to `CLAUDE.md`, which defines the authoring and build conventions. Each numbered section directory, such as `1.1-llm-internals/` or `7.3-nvidia-container-toolkit/`, contains a `README.md` with a suggested duration, a direct instruction link, an observable prerequisite/outcome table, and a Background list. These section READMEs are the canonical local inputs for the companion's curriculum manifest.

Participant-facing instruction files are named `*_instructions.md`, but their raw Markdown may also contain folded hints and reference answers. Author-only source and reference material includes `*_solution.py`, `*_reference.py`, `reference_solutions/**`, and tests that reveal expected behavior before an attempt. The spoiler-free progression rules in `.agents/skills/exercise-walkthrough/SKILL.md` are the source for the deployed tutor policy; the authoring skill itself is not injected or invoked wholesale at runtime. Its `.claude/` copy is not byte-identical; do not merge the two. Codex never receives raw instruction or test files: the backend parser injects only the learner-visible, progress-scoped projection for the current turn.

The AISB Python environment is large and has section-specific dependency constraints. Do not modify `<aisb-root>/requirements.txt` or reuse a lesson virtual environment. The companion has its own manifests and lockfile at `<companion-root>`.

The term “Codex gateway” below means the backend module that starts `codex app-server` as a child process using its default newline-delimited JSON stdio transport. It performs the required `initialize` request and `initialized` notification, correlates JSON-RPC request IDs, consumes App Server notifications while assembling a turn, returns the completed assistant response to the browser, and resumes persisted Codex threads after a backend restart. It does not currently expose token-by-token browser streaming or SSE replay.

The term “student source policy” means both the versioned teaching instructions and the enforced list of files and operations the tutor may access. It is not merely a refusal prompt. The path resolver canonicalizes real paths, rejects traversal and unsafe symlinks, and applies deny rules before a file is read, indexed, attached, searched, or offered to the model.

The term “prefill” in the implemented v1 means the deterministic and bounded reference-cache portion of preparation: discover verified external HTTPS links from learner-visible material manifests, optionally fetch public HTML/PDF bytes after an explicit action, create inert Markdown from valid HTML, and record immutable provenance. It does not mean captions, ASR, PDF text extraction, full-text indexing, or Codex-generated summaries. Retrieved text is external untrusted evidence, never instructions.

The term “preparation” in the implemented v1 means the explicit `/prepare` inventory/cache run around the verified curriculum manifests. Opening the page reads local run state only. **Inventory links** performs local discovery; **Inventory & cache public sources** is the only external-network action. Codex enrichment, generated day/lesson artifacts, captions/ASR, and PDF text extraction are deferred; the state contract reports them disabled rather than implying they ran.

The term “NowAnchor” means one immutable navigation snapshot containing the sampled absolute instant, capture source (`load` or `button`), stable router history-entry ID, bootstrap generation ID, programme time zone, schedule revision, resolved programme date/day state, active event-binding IDs, deterministic primary row, and fallback reason. Capture the instant before asynchronous schedule loading, bind it to the current entry/bootstrap, then resolve that same sample when schedule data arrives only if both IDs still match. It is not a live clock, a ban on ordinary action timestamps, a schedule record, Calendar sync cursor, or durable learning artifact.

The term “PageContextSnapshot” means the immutable, server-authoritative description of what a learner-facing route means at the instant the participant presses Send. It records the route/page kind, route history-entry ID, active tab, day/event/session IDs and displayed schedule fields, schedule revision and frozen `NowAnchor`, linked section/current exercise, the exact canonical outcome records shown on the page, the sanitized progress-scoped lesson projection, current note descriptor/live draft, relevant validated AISB file descriptors, repository identity/HEAD, and chat scope. It is built from domain records and IDs, never a DOM/HTML scrape, so opening a UI-only Answer/Solution fold cannot smuggle that body into model context. A `NoteDraftSnapshot` is its learner-authored note component: exact editor text at Send, `note_id`, kind, logical state-relative path, base revision, draft hash, save/offline/conflict state, and selected/current Markdown section.

The term “canonical outcome” means the byte-preserved observable outcome text and engineering/ML/security/theory category parsed from a section `README.md`. Its logical `outcome_id` combines section ID, category, and ordinal; a separate `outcome_version_id` hashes only that normalized individual outcome record. An unrelated README edit does not churn either ID. A text-only edit at the same section/category/ordinal creates a reviewable version under the same logical ID; moving an outcome between categories or ordinals creates a new logical ID and a migration proposal rather than pretending identity was preserved. A day outcome list is a deterministic aggregation of these records. A Codex-suggested outcome for a schedule item without a curriculum contract is explicitly `derived`, source-linked, and cannot silently become canonical.

The term “Imagegen” in the implemented v1 means the explicit `/visuals` workflow. The participant authors a typed `VisualAidBrief`, including factual constraints, exclusions, alt text, and an equivalent prose explanation; the server renders a fixed educational prompt; the participant reviews that exact prompt; and a one-use expiring confirmation permits at most one `gpt-image-2` request. Valid PNG bytes and immutable metadata are stored under the companion state root. No tutor, review, manager, or preparation turn invokes image generation implicitly, and generation never edits AISB or a note.

The term “AISB repository identity” means a local binding to the canonical Git common directory plus a fingerprint of the verified AISB remotes. It is never derived from the companion repository. Use it to namespace default runtime state. If the checkout moves, is recloned, or changes identity, require the user to reselect and rebind it rather than silently opening another state namespace or resuming threads against it.

The supported MVP is one participant on macOS, one configured AISB checkout, one loopback browser session, and an app-server child authenticated through that participant's Codex account. The backend and app-server never listen on a LAN interface. ## User Experience and Route Model

Use real URLs for every meaningful location. Client-only modal state may remain ephemeral, but day, event, active workspace tab, resource, and chat identity must survive hard reload and browser history navigation. The derived `NowAnchor` is route-navigation state, not durable learning data or a setting.

The implemented routes are:

- `/` for the once-per-load clock-oriented Today workspace and current programme day.
- `/day/:dayId` and `/day/:dayId/event/:eventId` for one local schedule day or explicitly selected event, its mapped outcomes, notes, review, and scoped tutor.
- `/notes/:noteId` for a known day, lesson, event, or named ad-hoc note identity.
- `/study/:dayId`, `/study/:dayId/section/:sectionId`, and `/study/:dayId/section/:sectionId/document/:documentId` for repository-led material, outcomes, notes, review, and section-scoped tutor context.
- `/prepare` for local reference inventory and explicit bounded public-source caching with immutable provenance.
- `/manager` for the one durable overall learning-manager conversation.
- `/visuals` for participant-authored educational briefs, exact-prompt confirmation, and the immutable local visual library.
- `/backup` for explicit verified export and honest manual-fresh-state restore guidance.
- `/diagnostics` for local runtime boundaries plus the explicit Codex account/model/profile self-test.

Review remains embedded in the Today/Study workspace rather than owning a separate route. Schedule editing, event-to-curriculum linking, note selection, and VS Code handoff also stay within the workspace. There are no `/prefill`, `/resources`, `/settings`, standalone `/review`, or automatic-restore routes in v1.

The shell captures one `NowAnchor` navigation sample before asynchronous schedule loading on each full document load, binds it to the current stable history-entry/bootstrap IDs, then creates the `NowAnchor` from that exact sample once the schedule is available and the IDs still match. A late response for an entry the participant has left is discarded; it cannot resample, redirect, scroll, or overwrite the new entry. The anchor contains `captured_at`, `capture_source`, both IDs, `programme_time_zone`, `schedule_revision`, the resolved date/day state, all active event-binding IDs, and a deterministic primary row for scrolling. Compare absolute instants, not browser-local clock labels, against RFC3339 event timestamps and display the result in `Europe/London`; a device in another time zone therefore selects the same programme instant. Label the quiet persistent control “Sync to now,” not “Sync,” and pair it with status such as “Synced 10:32 · Europe/London” plus a tooltip explaining that it uses the system clock and does not change the schedule.

Resolve the anchor from non-cancelled events using half-open bounds `start <= captured_at < end`. Prefer active timed events; when sessions overlap, highlight the whole active group and choose the primary row by start time then `event_binding_id`. If no timed event is active, select the next timed event; before the first item select that first item, between items select the next item, and after the last item retain the last completed row with an end-of-day state. Show all-day items without letting one mask a concurrent timed session; use an all-day item as primary only when there is no timed item. The explicit mapping governs Day 1–7, including the Day 5 break and its events; the post-programme departure date gets a labelled non-day state. Before the programme, show the first day/next start; after departure, show a programme-complete state rather than inventing Day 8.

Auto-anchoring may choose the displayed day and scroll a schedule row into view only on the unqualified `/` entry, replacing that entry's history snapshot rather than adding a surprise Back step. It must not open a lesson/event, steal keyboard focus, or override an explicit `/days/:dayId`, `/events/...`, lesson, note, chat, resource, review, manager, repository, preparation, settings, or diagnostics route. On an explicit current-day route the matching row may be highlighted, but the route is never redirected. Pressing “Sync to now” is an explicit request from any route: it samples again, reads the current local schedule revision, pushes a history entry for the applicable day/schedule position, and scrolls without opening the event. Back returns to the prior route and frozen anchor; forward restores the newer one. A `popstate` or bfcache restoration uses its history entry unchanged, while a hard browser refresh intentionally replaces the current entry's anchor with a fresh sample. Respect reduced motion and never animate in a way that delays navigation.

There is no wall-clock interval, scheduled callback, background rollover, or polling. If the local schedule revision changes after capture, keep the old selection and show “Schedule changed since sync”; if its primary row no longer exists, show the frozen time with an unavailable-target state. Do not silently choose another event. The next explicit refresh or “Sync to now” recomputes against the edited schedule. Manual day/event selection overrides the displayed view without rewriting the frozen timestamp. “Take notes now” uses the actual creation time for identity/frontmatter but proposes links from the frozen anchor until the participant explicitly resynchronizes.

The week overview is a calm operational surface, not a marketing dashboard. The selected visual thesis is a beautifully typeset field notebook translated into a dependable learning workspace: warm paper, near-black ink, restrained cobalt orientation/action, editorial headings, a clear time rail, and minimal chrome. The primary workspace is the dominant plane; navigation is a narrow week/day rail and secondary context lives in a collapsible inspector rather than a grid of generic cards. Notes remain the visual centre of gravity. Implement the selected warm direction directly; do not average it with the rejected cool studio candidate.

On note-bearing day, lesson, event, and ad-hoc-note routes, treat the left sidebar, schedule region, and tutor/chat pane as three independent layout regions. Each has a persistent, keyboard-operable control with an unambiguous accessible name and correct `aria-expanded`/`aria-controls`; the collapsed edge has a visible way back and does not depend on an unlabeled chevron. The note header also offers “Focus notes,” which collapses those three regions in one layout transaction and changes to “Exit focus.” Preserve the exact pre-focus arrangement so exit is reversible even when only some panels were originally open. The autosave status, note title/context, and recovery/conflict state remain visible in focus mode; canonical outcomes remain reachable through a compact disclosure rather than disappearing.

`focusNotes` has one valid invariant: all three panel-expanded flags are false, `activeOverlay` is empty, and a complete pre-focus snapshot exists. While focused, pressing an individual collapsed-edge control exits focus, restores the snapshot, and then opens the requested panel; pressing “Exit focus” simply restores the snapshot. Navigating to another note-bearing route carries focus and its snapshot into the new entry by default. Navigating to a non-note route creates a destination-safe, non-focus layout, while Back can still restore the prior focused entry. Entering focus again is idempotent and never overwrites the original pre-focus snapshot.

Collapsing a region changes presentation, not ownership or lifecycle. Do not discard or reconstruct the Markdown editor engine's complete state—including value, cursor, selection, composition, and undo/redo history—or the chat composer's draft and live turn subscription. Do not interrupt a Codex turn, change the active workspace tab, alter the selected schedule row, or take another `NowAnchor` sample. A collapsed chat edge shows streaming/unread/error state and reopens the same conversation. A collapsed schedule edge shows the selected/current session, frozen sync time, schedule-stale state, and “Sync to now.” A collapsed sidebar edge shows the current day and an “Expand navigation” control.

At compact/mobile widths, sidebar, schedule, and chat become mutually exclusive overlay drawers while notes remain the background workspace; opening one closes any other visible overlay without erasing the semantic expanded/pre-focus flags used at wider widths. A drawer traps focus, marks the background inert, closes on Escape, and returns focus to its opener. At 200% zoom use the same compact projection before horizontal clipping occurs. A pre-focus snapshot stores semantic panel flags, not pixel geometry, so a viewport change maps it to the safe one-drawer projection and returning to desktop restores the intended regions.

Panel toggles update the current history entry with `replaceState`, not `pushState`, so focusing does not pollute the Back stack. The update merges namespaced layout data into existing router state; it may not clobber route keys, the `NowAnchor`, bootstrap/entry IDs, or saved scroll position. Store the last non-sensitive semantic panel arrangement—including `focusNotes` and its complete pre-focus snapshot—in versioned browser-local UI preferences for reload/reopen, but never persist an open `activeOverlay`; a fresh document rehydrates drawers closed. A valid per-entry layout snapshot wins during Back/Forward restoration and responsive defaults apply only when neither exists. Restore panel geometry/projection before restoring scroll so the saved location remains accurate. Layout restoration must not override an explicit route or `NowAnchor`; a sync/navigation action carries the current layout into its new entry unless the destination has a route-specific safe default.

The overview content is the seven-day rail, today/next-event orientation, required reading state, review-due state, and one clear Continue action. A day page presents the schedule, the day's canonical outcomes grouped by engineering/ML/security/theory with source-section links, and a restrained Edit schedule mode. Its outcome text and IDs are the same records shown in the corresponding lessons, tutor inspector, and review coach. The schedule editor can add an item, change title/time/location/kind/lesson links, move an item to another day, or mark it cancelled; it uses the same conditional atomic write contract as other structured state. A lesson or event page's single job is to let the participant work. The manager page's single job is review and planning.

Use three restrained motions: a shared position/opacity transition from a day schedule row into its event workspace, a brief save-state pulse that changes from Saving to Saved without moving layout, and streamed chat/tool state that expands in place. Respect reduced-motion settings and never delay navigation or saving for animation.

Every scheduled event has notes. Classification selects the starting workspace, not the available data:

- Speaker, lecture, or talk events open notes first with a template for key ideas, questions, follow-ups, and references.
- Pair-programming, lab, or exercise events open the lesson/tutor workspace with notes and test status alongside it.
- All other events open notes first.

Classification uses explicit deterministic keyword rules and a saved user override. It must never depend on an opaque model guess. Every seeded event already has a companion-owned immutable `event_binding_id`; locally created events receive one before publication. Routes, notes, chats, and schedule edits use that ID. Title, day, time, location, classification, linked lesson, and cancellation state are mutable attributes, never identity. The local schedule contains no external event alias.

Lesson surfaces render the same sanitized participant projection used by retrieval, with executable code fences, safe links, the canonical prerequisite/outcome panel, and the current exercise visibly identified. Unrevealed folds and later exercises are absent from the rendered document rather than merely hidden with CSS. Section and document choices use visible wrapping rows or a vertical list with full labels; they must not rely on clipped text or an invisible horizontal scrollbar to reveal additional material. The tutor receives the exact applicable outcome IDs/text and starts from “What you are working toward,” then relates hints and reflection prompts to those outcomes. For coding help, the participant explicitly selects the current answer file and either a line range or “current exercise” excerpt; the selector previews exactly what will be sent. The manager cannot enumerate or search all answer files.

## Student Progress and Reveal Model

Generated media is immutable and lives only under `media/generated/`, never in AISB or the companion Git checkout. `manifest.json` records immutable generation facts: an opaque asset ID, content hash, originating scope ID and frozen-context hash, outcome/source hashes, exact sanitized prompt, provider/model/version, quality, dimensions, MIME type, generation time, provider request ID and usage/cost when available, initial alt/prose drafts, and moderation result; it never records a credential. Reviewed accessibility-copy changes, staleness, supersession, note insertion, export, deletion, and missing-byte state are append-only events in `media/events.jsonl`; `media/index.json` is a rebuildable current projection, not history or authority. Decode provider output to a bounded supported raster format, validate dimensions/MIME, strip metadata, build and flush a complete temporary asset directory containing the image and manifest, atomically rename that directory to its final ID, flush the generated-media parent, append/flush the publication event, and only then advance the index. Serve assets by opaque same-origin ID. Do not preserve an expiring remote URL or OCR/index generated pixels as factual evidence. Regeneration or variants create a new asset plus a supersession event; they never overwrite an accepted asset or rewrite its manifest.

Every note begins with YAML frontmatter containing schema version, immutable `note_id`, `note_kind` (`day`, `lesson`, `event`, or `ad_hoc`), title, created/last-modified time, revision, and typed links that apply: programme day, section IDs, canonical outcome IDs, event-binding ID, start/end/time zone, and status. Content below the frontmatter is ordinary participant Markdown. Derive canonical relative paths only from validated application-owned day/section/event/note IDs and, for ad-hoc notes, the validated creation date; never trust a frontmatter- or index-supplied path. Canonicalize beneath `<state-root>/notes`, reject traversal, symlinked parents/targets, path-shape mismatches, and duplicate IDs, and quarantine mismatches for repair. `notes/index.json` is a rebuildable projection from those validated paths/frontmatter, not path authority. It is written conditionally and atomically so URLs do not depend on titles or rescheduling. Two events linked to the same section open the same lesson note, while their event notes remain separate. Ad-hoc notes keep their creation-date path even if the participant later links them to a day, lesson, event, or outcome.

Create day and lesson notes lazily on the first explicit open. “Take notes now” uses a collision-safe timestamp plus immutable note ID, exclusively creates the Markdown file and first revision before route navigation, and defaults to the configured local date/current programme day. It may suggest the nearest active event or lesson, but ambiguous or out-of-programme capture remains an unlinked ad-hoc note. Relinking an event preserves its event note unchanged; the event's lesson association switches to the destination section's independently owned lesson note and never moves or merges either lesson note. Relinking an ad-hoc note changes only its typed frontmatter/index relations and never moves its file. Rescheduling or reclassifying changes listings/workspace choice while the immutable event URL stays stable. Local cancellation retains the binding, note, and chat in a cancelled/orphaned-notes view.

Autosave has two independent layers for every note kind. The client writes the exact draft and its base revision to IndexedDB on every change. An “accepted keystroke” means the IndexedDB transaction committed and the UI announced “Saved locally”; arbitrary process-kill tests begin only after that state. After three seconds without a newer edit, the client sends one trailing conditional update carrying the last acknowledged content hash. The backend writes a temporary sibling, flushes the file, atomically renames it over the Markdown file, flushes the parent directory where the platform supports it, appends `notes/revisions/<note-id>.jsonl`, and returns the new hash. Retain the most recent 50 revisions and one daily revision for 30 days, with settings to extend retention. The UI announces Saving, Saved, Saved locally/retrying, or Conflict. On reload it compares IndexedDB with disk and offers recovery; it never silently overwrites a divergent revision. Use `BroadcastChannel` or a writer lock to prevent two tabs from silently replacing one another. Valid manual Markdown/frontmatter edits are reloaded; malformed or duplicate note identity produces a visible diagnostic and recovery copy without discarding either version. Do not rely on `beforeunload`.

The immutable repository seed is `config/schedule/aisb-example-week.snapshot.json`. Its schema records a stable seed ID, creation time, half-open programme window, `Europe/London`, an explicit date-to-`day1`…`day7` map, an explicit post-programme departure date, expected event count, reviewed event-array SHA-256, privacy manifest, and the ordered generalized events. Every event has a companion-owned `event_binding_id`, nullable `programme_day_id`, title, start/end, all-day state, status, and optional location. `events_sha256` is SHA-256 over the exact UTF-8 RFC 8785 JSON Canonicalization Scheme serialization of the `events` array, with no trailing newline or surrounding document fields; record this as `events_hash_algorithm: sha256-rfc8785-events-array` and use the same implementation in validation tooling.

Seed validation rejects unknown top-level/event keys and asserts: exact count/hash; unique IDs matching `^aisb-2026-[0-9]{3}$`; strict RFC3339 timestamps with `end > start`; coherent all-day representation; event overlap with the half-open programme window; chronological order; bounded non-empty titles; the status enum; the explicit programme-day/date relationship; and nullable day IDs only on declared non-programme dates. Scan every allowed string value for URLs, email addresses, meeting tokens, control characters, and suspicious opaque identifiers. Public-release review additionally confirms that titles contain no speaker attribution and that exact programme venues, accommodation, and visit destinations are absent. Reject any Google identifier, description, attendee, joining link, attachment, event URL, or authentication field.

On startup, `seedIfAbsent` validates the tracked seed and exclusively creates `<state-root>/schedule/schedule.json` only when that runtime file is absent. Creation is a deterministic seed-to-runtime transform, not a byte copy: retain every hashed seed field, add top-level `schedule_revision: 1`, and add per-event `local_revision: 1`, a deterministic initial kind, and initially empty linked-section IDs. The working file records `schema_version`, `seed_id`, `seed_events_sha256`, seed capture/window/time-zone/day-map provenance, and the ordered runtime event records. Tests project each fresh runtime event back to the allowed seed fields and require that RFC 8785 projection to equal `seed_events_sha256`. Repeated startup, application upgrade, or a changed packaged seed is a no-op once runtime state exists. There is no reseed button. A deliberate future seed migration would require a new reviewed plan and explicit local merge UI.

`schedule/schedule.json` is versioned, formatted JSON and the sole editable schedule source of truth. Each event records immutable `event_binding_id`, title, start/end, optional location, deterministic or overridden kind, linked section IDs, status, and a local revision. Create, edit, move, classify, link, and cancel operations require the expected schedule/event revision and write one complete temporary sibling, flush it, atomically rename it over the current file, and flush the directory where supported. Valid external edits are loaded on refresh; schema-invalid or hash-inconsistent edits produce a diagnostic and keep the last valid in-memory state. Corrupt state is quarantined or restored from a valid local revision/recovery copy; it is never silently replaced from the seed.

The runtime contains no Google SDK, OAuth route, Calendar credential, import history, polling timer, external event alias, re-import merge, or schedule network request. A network spy must observe zero Google requests across launch, settings, diagnostics, navigation, preparation, manager use, schedule editing, and recovery.

The client clock anchor is deliberately outside `schedule/schedule.json` and durable application state. It cannot change a schedule revision or event field. Keep it only in the active router/history entry so in-app back/forward can restore the exact captured time, resolution, scroll target, and schedule revision; a full document load replaces the current entry's anchor snapshot, while the explicit button pushes a new one. Resolve from a small injected `Clock.now()` boundary so tests never depend on the machine clock. “Sync to now” is clock/view synchronization, not Calendar or schedule synchronization.

Use the tracked example programme-date mapping exactly: Days 1–7 cover 2026-08-30 through 2026-09-05, with Day 4 schedule-only, and 2026-09-06 is a non-programme departure date with `programme_day_id: null`. Never derive this identity from the current date, array position, or an editable start-date setting. Keep the repository hierarchy separate: the reviewed programme projection maps Day 5 to repository `4.*`, while Study enumerates repository day/section identities directly. Event-to-section bindings are explicit ordered records. Deterministic title matches or Codex may propose a binding for review, but cannot silently publish one. Preserve accepted bindings by immutable companion event-binding ID across title, time, day, and cancellation changes.

Preparation is a durable, explicit three-stage pipeline. Stage 1 needs neither network nor Codex authentication: scan the AISB manifest, extract canonical prerequisite/outcome records, create a spoiler-free section overview projection and progress-scoped lesson projections, discover allowed prerequisite/Background/reference links from section READMEs and already-visible lesson material, and identify schedule-to-section gaps. The overview projection contains the section framing and contract but no exercise body or gated fold; a progress projection stops at the current exercise and applies the normal reveal policy. Classify each resource as required, optional longer reading, or reference and record day, section, source URL/local path, any stated time window, and the Git commit that discovered it. This stage makes week/day/lesson outcome pages useful immediately.

Stage 2 is prefill. The bounded application worker—not Codex—fetches and normalizes selected public resources into immutable local cache objects; caching a future resource does not make it retrievable by a learner-facing scope. Stage 3 is optional Codex enrichment. Up-front no-tool preparation threads receive only section overview projections, canonical outcomes, schedule fields, and selected cached background chunks. Once the participant reaches an exercise, an explicitly requested refresh may instead receive that exercise's progress-scoped projection. Depending on the reviewed artifact request, preparation may propose a day overview, lesson preview/knowledge map, event-to-section/outcome mapping, source-grounded resource summary, glossary, tutor starter prompt, or active-recall question seed. A job may additionally run a capped number of separate no-tool visual-planner turns over the same or narrower sanitized inputs to return `VisualAidBrief`s. Neither kind of turn may create a solution, reference answer, hidden test explanation, future-exercise summary, or new canonical curriculum contract. Question seeds are not shown as feedback until used in a review session after a learner attempt. Visual briefs are proposals only: preparation never calls the image provider, and the participant must review and explicitly generate each selected raster visual later.

Before starting, `/prepare` reads the latest local manifest and shows a preflight with target days/sections, proposed local rescan work, every URL/domain and expected fetch class, stale/missing cache counts, requested artifact types including the requested number of visual briefs, and the number/model/effort of proposed Codex turns. Visual briefs default to zero and have a hard maximum of six per preparation job; requests over the cap are rejected rather than truncated silently. The image-generation count is always zero at this stage. “Prepare week” is a first-run call to action, not an automatic launch action. Refresh local scan and Start network/model work are explicit controls; launch, restart, navigation, due-date calculation, and visits to `/prepare` or `/review` cause zero fetches, zero Codex turns, and zero image requests. Allow narrower day/section selection and deterministic-only preparation when Codex is unauthenticated. One preparation turn runs at a time per thread with bounded global enrichment concurrency.

Fetch only `http` and `https`. Resolve and validate every destination IP at connection time and again after every redirect; reject loopback, private, link-local, multicast, metadata-service, and other non-public ranges for both IPv4 and IPv6, and prevent DNS rebinding by connecting only to the validated address while preserving TLS hostname checks. Set time and size limits, honor conditional requests, and make every job retryable. Strip active HTML and scripts. Convert ordinary HTML to Markdown with article extraction, convert PDFs to Markdown/text while retaining page markers, and prefer publisher-provided captions for videos. Local speech-to-text is post-MVP; never silently download video/audio or bypass access controls.

Expose the complete pipeline through `POST /api/preparation/jobs`, `/prepare`, and `npm run prepare -- --week|--day <n>|--section <id>`. Expose Stage 2 directly through `POST /api/prefill/jobs`, `/prefill`, and `npm run prefill -- --day <n>|--all`. All entrypoints create compatible durable stage/job records. Limit work to three concurrent fetches, one conversion per media type, and one enrichment turn per preparation thread; support cancellation between bounded stages, persist per-resource/artifact status, and resume incomplete jobs after restart. Retry transient fetch failures with capped exponential backoff; authentication, policy, size, unsupported-format, and invalid-model-output failures require an explicit user retry.

Key a preparation plan by AISB repository identity/commit, schedule seed hash and current local schedule revision/hash, canonical outcome/projection hashes, selected cache-manifest hashes, artifact kind, requested visual-brief count, visual-utility-rubric version, developer-prompt and scope-supplement hashes, model/effort, and output-schema version. The same completed key is a no-op; a partial job resumes from its last durable boundary without duplicating a successful fetch or model turn. Changed inputs mark dependent artifacts stale and regenerate only affected sections when approved. Never silently apply a generated event mapping or derived outcome.

Preparation artifacts are immutable. Each records job/thread/turn IDs, generation time, model/effort, prompt/schema versions, complete source citations/hashes, validation status, and optional superseded artifact ID—never later approval state. Every completed scan, prefill, or enrichment stage also writes one immutable `preparation/results/<result-id>.json`: a scan result snapshots manifest/outcome/projection hashes, a prefill result references exact cache-manifest IDs, and an enrichment result references its validated artifact ID. At a completed stage boundary, write and flush all immutable primary objects first, write/flush the immutable typed stage result, then conditionally and atomically replace the one `preparation/jobs/<job-id>.json` file containing the completed-stage number and current result ID, and flush its parent directory. A crash exposes the prior job pointer or the complete new pointer; an unreferenced immutable result/artifact is harmless and discoverable during recovery.

Record approve/reject decisions append-only in `preparation/approvals.jsonl`, keyed by artifact ID/hash, decision/operation ID, and expected target-state revision. Approval uses a hash-bound preview and conditionally atomically updates exactly one working file such as `schedule/schedule.json` or `learning/derived-suggestions.json`; that file records the operation ID so a crash between target update and result-journal append can be reconciled without double application. Rejection changes no target. Kill-point tests cover artifact flush, job-pointer replacement, approval intent, target replacement, and approval result.

Each immutable cache object records original URL, retrieval time, content hash, MIME type, extraction tool/version, title, language, license/status when known, transcript source and timestamps, and any failure. Refresh creates a new object and moves only the manifest pointer. Re-running prefill with unchanged content creates no duplicate.

Index permitted visible curriculum chunks, canonical outcomes, approved generated preparation artifacts, notes, permitted chat/review messages, current schedule events, and cached source chunks in SQLite FTS. Do not require an embedding service or vector database for this one-week corpus. Keep the database fully rebuildable from the primary Markdown, JSON, and JSONL files above. Every result carries a local artifact path and original source URL where applicable. Treat human-authored seed text, fetched content, and model-generated chunks as untrusted when assembling a turn; mark application-owned note/schedule metadata separately. Cap the number and total size of chunks sent to a model.

## Workspace and Editor Launch Boundary

During curriculum scanning, create a `ParticipantFileDescriptor` only when visible setup prose unambiguously names a participant working file inside the current section. It records section/exercise IDs, source/projection hashes, repository-relative target, visible scaffold blocks through the current exercise, and a best-effort cursor marker. Reject absolute paths, traversal, symlinks, targets outside the section, directories, Git internals, and any path classified as solution/reference/test/raw-instruction material. Do not infer an instructor `*_solution.py` target from the fact that AISB uses solution files as its authoring source.

`Open in VS Code` is a direct user-to-application action. `previewOpen` returns either an existing-file launch token or an absent-file create token, each bound to the validated AISB/section/target/source state. Opening an existing regular participant file is read-only. Creating a missing file first shows the target and scaffold diff; its create token binds AISB repository identity, HEAD, section/source/scaffold hashes, canonical target, and the observed absent state. Write and `fsync` a same-directory companion-owned temporary file, publish it with `link(temp, target)` so an existing target fails atomically, `fsync` the directory, unlink the temporary name, and `fsync` the directory again. Successful creation returns a new launch token bound to the published regular file; the consumed absent-state token cannot be reused for launch. Startup cleanup may remove only stale companion-owned temporary names, never a published target. If the target appears, source changes, or validation fails between preview and apply, leave it untouched and require a new preview. Repeated clicks are idempotent. Creation does not stage, commit, branch, run a lesson, or start a model turn. Add crash/race tests at temporary write/flush, link, each directory flush, and temporary unlink.

After validation/creation, invoke VS Code with a fixed executable and argument array, no shell interpolation, `cwd=<aisb-root>`, `<aisb-root>` as the opened folder, and `--goto` for the exact participant file and resolved line. Treat editor launch and file creation as separate result fields. If launch fails, retain a successfully created file, show its full/repository-relative paths and a safely rendered copyable command, and allow launch retry without another write. Tests use a fake launcher to assert arguments containing spaces and shell metacharacters are passed literally. The real macOS fallback is enabled only after a contract test proves it opens the AISB folder and file together; otherwise the app explains how to install the `code` shell command. VS Code may offer to reopen the AISB root in its checked-in dev container, but the companion never accepts that prompt or changes the environment automatically.

## Idempotence and Recovery

The implemented v1 uses content hashes, stable application IDs, conditional writes, idempotency keys, immutable cache/media objects, and conservative uncertain-delivery states for curriculum discovery, first-run schedule seeding, local schedule writes, preparation inventory/cache, review/tutor/manager turns, workspace create/launch, transcript projection, visual confirmation, backup export, and note saves. The older paragraphs below that discuss preparation enrichment, durable image-job journals, SQLite/index rebuild, or automatic restore describe post-v1 hardening ideas rather than implemented recovery behavior.

Client rerenders, React strict-mode development remount checks, asynchronous schedule completion, SSE reconnect, note autosave, tab visibility changes, and bfcache/`popstate` restoration must not take another `NowAnchor` navigation sample or replace an existing anchor. Initial bootstrap captures at most once per full document load even when initialization retries; retain that sample with stable entry/bootstrap IDs until the schedule can resolve it. If those IDs are no longer current, discard the late resolution. Only the explicit “Sync to now” handler takes another navigation sample during the document lifetime, and a double-click is coalesced into one navigation/history update. A hard refresh begins a new document and may sample once again. Ordinary time reads for note/chat/save/audit timestamps are independent and cannot feed the navigation resolver.

Never overwrite a note whose acknowledged revision differs from disk. Keep the browser draft, write a conflict copy, and let the user choose. If an atomic save fails after writing the temporary file, the original Markdown remains valid and startup cleanup may remove only stale companion-owned temporary files. Rebuild `notes/index.json` from valid immutable frontmatter when needed; duplicate or invalid identities remain quarantined for explicit repair rather than being renamed automatically.

If app-server exits, mark the gateway unhealthy, keep notes and navigation working, restart with bounded backoff, reinitialize, resume known threads, and reconcile completed history. Do not replay an uncertain user turn automatically. Offer Retry only after explaining whether a completed turn was found.

If first-run schedule creation is interrupted, exclusive creation and atomic publication expose either no runtime schedule or the complete validated seed copy; retry only when the file is still absent. Once runtime state exists, never seed over it. If the working schedule is corrupt, quarantine it or recover a valid local revision with a visible diagnostic; never use the packaged seed as a silent reset. Cancelling a local event never deletes its notes or chat.

If prefill fails, keep the previous manifest pointer and record the new failure. Do not replace a good cache object with an error page. A cache rebuild may delete only unreferenced companion-owned objects after a dry-run preview.

If preparation enrichment is interrupted or its result is uncertain, inspect the bound thread/turn before offering retry. Publish validated immutable primary objects and their typed stage result before atomically advancing the job file's result pointer; never launch a duplicate turn solely because the browser disconnected. Reconcile unreferenced complete results/artifacts by job/turn/key, and remove only failed companion-owned temporary files. Invalid output records a typed failure and retains the last valid pointer. Reconcile an uncertain suggestion approval from the operation ID embedded in the target working file and its append-only approval journal. If review feedback is interrupted after the learner response was saved, resume/reconcile the same review turn; never ask the learner to overwrite the saved response or show partial feedback as final.

Before an image request, durably write a pending job whose one-use confirmation token binds the origin scope/progress snapshot, frozen context, source/outcome hashes, exact prompt hash, provider/model/quality/dimensions, count of one, destination, non-secret provider-configuration revision, random backend boot epoch, and expiry. Never store a key hash or fingerprint. Consume the token conditionally before the provider call. A restart changes the boot epoch and invalidates every unstarted confirmation. If the response arrives, validate/decode into a complete companion-owned temporary asset directory, flush its image/manifest/directory, atomically rename the directory, flush the parent, append/flush the publication event, and then advance `media/index.json`; kill-point tests at every boundary expose the prior index or a discoverable complete new asset, never half an asset. If the process loses the response after dispatch, record `unknown` with any provider request ID and do not automatically retry or claim cancellation; a later explicit retry creates a new job and warns that the prior request may have been charged. Provider errors and invalid outputs retain prior valid assets. Source, prompt, or model changes create a new asset and event; accessibility-copy review and staleness append events without mutating factual generation provenance.

If participant-file creation succeeds and VS Code launch fails, record partial success and retry only the launch. If another process creates the target after preview, refuse the write and open nothing until the participant reviews the existing file. Never delete, truncate, append to, or “repair” an existing AISB participant file during recovery.

Runtime state lives outside both repositories, and application source lives outside AISB, so switching or updating AISB branches cannot remove notes or the running companion. Export creates a new timestamped JSON backup, excludes authentication material and both repositories, includes allowlisted browser recovery state, never mutates source files, and is downloaded only after browser-side hash verification. The manifest contains manual fresh-state guidance and explicitly records that automatic restore is unavailable. Any recovery from that file is therefore a deliberate manual procedure: inspect/verify it, populate a new state root, reselect/revalidate the machine-local AISB checkout, and reconnect Codex authentication as needed. The application does not write a restored state root, swap an active pointer, validate restored thread bindings, or claim that a restore drill passed. Imagegen availability after manual recovery still depends only on the newly launched backend inheriting `CODEX_OPENAI_API_KEY`.
